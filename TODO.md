Целевая схема

QML-страницы и диалоги
        ↓ команды / модели / состояния
C++-слой приложения: сервисы и модели для QML
        ↓ интерфейс источника данных
Mock-провайдер (сейчас)  →  HTTP-провайдер (позже)
                                 ↓
                         Go API → PostgreSQL

QML оставляем для экранов, навигации, форм, отображения данных и состояния интерфейса. C++ клиентского приложения отвечает за модели таблиц, вызовы сервисов и обработку результатов. На сервер переедут сохранение данных, правила доступа и расчёты, результатами которых клиент будет пользоваться. Не нужно делать C++-клиент «будущим backend»: Go-сервис будет отдельным приложением.

План работ

1. Согласовать границы и контракты. Описать основные сущности и поля: актив, риск, мера, связь между риском и мерой, настройки модели, пользователь и сводные показатели. Для будущего API определить операции и формы ответов: списки, создание/редактирование/удаление, привязка меры, импорт сценария, Dashboard. В ответах сервера предусмотреть рассчитанные балл, уровень риска, потери и ROSI, чтобы не дублировать расчёты в клиенте. Уточнить спорные правила текущей модели до переноса — например, связь риск-аппетита с границами уровней и OT-поправку.
2. Добавить C++-фасад для QML. Создать сервисы приложения, например  AuthService ,  AssetService ,  RiskService ,  MeasureService ,  DashboardService . Предоставить их QML через регистрацию типов или context properties. Интерфейс сервисов должен быть одинаковым для mock- и HTTP-режимов.
3. Сохранить работоспособность без backend через mock. Вынести демонстрационные наборы из  DataStore.qml  в  MockDataProvider /mock-сервисы. Они будут возвращать данные и имитировать операции с понятными статусами загрузки и ошибками. Mock авторизации не должен выглядеть как настоящая проверка: достаточно явно демонстрационного входа; реальные пароли не следует переносить в клиентский код.
4. Перевести QML со  DataStore  на фасад постепенно. Сначала активы и их диалог, затем риски, меры и связь между ними. Страницы получают модели и вызывают команды сервисов, а не меняют массивы напрямую. Так можно сохранять текущий внешний вид и поведение по частям.
5. Заменить локальные расчёты контрактом сервера. Пока backend не готов, mock может возвращать заранее определённые или локально рассчитанные результаты. Но расчётную логику нужно изолировать от QML и явно пометить как временную. После появления Go API источником истины становится сервер; клиент только отображает полученные значения.
6. Подготовить подключение Go API. Реализовать  Http...Provider  с настройкой адреса API, сериализацией DTO, токеном авторизации, обработкой HTTP-ошибок и отменой запросов. Для начала можно оставить его неактивным, но с интерфейсом, совпадающим с mock-провайдером.
7. Разделить справочник БДУ и рабочие данные. Для первого этапа mock использует встроенную копию справочника. В будущем интерфейс  ThreatCatalogProvider  позволит заменить её на API или SQLite-кэш без изменения диалога импорта. Версию и дату актуальности справочника показывать отдельно; локальная SQLite-копия должна быть кэшем, а не вторым независимым источником истины.
8. Убрать старый  DataStore.qml . После перехода страниц поэтапно удалить из него CRUD, демо-пользователей, пресеты и расчёты. Не держать параллельно старый singleton и новые сервисы дольше необходимого — иначе появятся два изменяемых состояния, которые будут расходиться.
9. Проверить каркас тестами. Добавить тесты на DTO/модели и mock-сценарии, а для HTTP-провайдера — проверки сериализации и обработки типовых ошибок. Когда появится backend, интеграционные проверки будут выполняться против Go API и тестовой PostgreSQL.

Что добавить в проект на первом этапе

Ориентировочная структура клиентского кода:

src/
  services/          # интерфейсы сервисов приложения и состояния операций
  providers/
    mock/            # текущие демо-данные и mock-операции
    http/            # будущие HTTP-провайдеры с TODO
  models/            # типизированные данные и модели списков для QML
  dto/               # контракты запросов и ответов будущего API

В UI желательно унифицировать состояния операций:  loading ,  error ,  ready ,  empty . Тогда мок и HTTP-провайдер будут показывать ошибки и загрузку одинаково. Текущие сообщения об успехе, например экспорт отчёта, должны выставляться только при успешном результате операции.

Критерий завершения каркаса: приложение продолжает запускаться без backend; QML не читает и не изменяет реестры напрямую; страницы обращаются к сервисам; mock-сервисы позволяют пройти основные сценарии; точки подключения HTTP и авторизации обозначены в C++ и не маскируются под работающий backend.
